### [CRITICAL] Rule 001: Missing signer check on set_admin: any caller can rotate the vault admin

**File:** `src/lib.rs:38`

**Description:** The `SetAdmin` context accepts a `caller: Signer<'info>` but never verifies that `caller` is the current `vault_state.admin`. Any arbitrary signer can call `set_admin` and replace the admin with a key they control, then collect all fees or manipulate vault parameters.

**Vulnerable code:**
```rust
pub struct SetAdmin<'info> {
    #[account(mut)]
    pub vault_state: Account<'info, VaultState>,
    pub caller: Signer<'info>,
}

pub fn set_admin(ctx: Context<SetAdmin>, new_admin: Pubkey) -> Result<()> {
    ctx.accounts.vault_state.admin = new_admin;
    Ok(())
}
```

**Recommendation:** Add a `has_one = admin` constraint (and rename `caller` to `admin`) so only the current admin can rotate authority:
```rust
#[derive(Accounts)]
pub struct SetAdmin<'info> {
    #[account(mut, has_one = admin)]
    pub vault_state: Account<'info, VaultState>,
    pub admin: Signer<'info>,
}
```

**Reference:** [rules/001-missing-signer-check.md](rules/001-missing-signer-check.md)

### [CRITICAL] Rule 001: Missing owner/authority check in collect_fees: anyone can drain the vault to any recipient

**File:** `src/lib.rs:107`

**Description:** The `collect_fees` handler transfers tokens from the vault to `fee_recipient` without verifying that `caller` is the vault admin or that `fee_recipient` is the authorized fee destination. Any signer can invoke this to send arbitrary amounts of vault tokens to any token account they control.

**Vulnerable code:**
```rust
pub fn collect_fees(ctx: Context<CollectFees>, amount: u64) -> Result<()> {
    let vault_data = ctx.accounts.vault_state.try_borrow_data()?;
    let vault_bump = vault_data[42];
    drop(vault_data);
    // No check that caller == vault admin
    // No check that fee_recipient is the authorized destination
    ...
    token::transfer(cpi_ctx, amount)?;
}
```

**Recommendation:** Use a properly typed `Account<'info, VaultState>` for `vault_state`, add `has_one = admin` on it, require the caller to be that admin (rename `caller` to `admin`), and store/enforce an authorized `fee_recipient` pubkey in `VaultState`. Example:
```rust
#[account(mut, has_one = admin)]
pub vault_state: Account<'info, VaultState>,
pub admin: Signer<'info>,
#[account(mut, address = vault_state.fee_recipient)]
pub fee_recipient: Account<'info, TokenAccount>,
```

**Reference:** [rules/001-missing-signer-check.md](rules/001-missing-signer-check.md)

### [CRITICAL] Rule 002: vault_state in CollectFees is an untyped AccountInfo with no owner check

**File:** `src/lib.rs:176`

**Description:** `CollectFees.vault_state` is declared as `AccountInfo<'info>` (with `/// CHECK: vault global state — not type-checked`). The handler borrows raw bytes at a hardcoded offset to extract the bump, with no verification that this account is owned by the current program or that its discriminator matches `VaultState`. An attacker can pass a crafted account with a chosen bump byte at offset 42, causing the program to sign with an arbitrary PDA seed and drain an unintended vault token account.

**Vulnerable code:**
```rust
/// CHECK: vault global state — not type-checked
pub vault_state: AccountInfo<'info>,
...
let vault_data = ctx.accounts.vault_state.try_borrow_data()?;
let vault_bump = vault_data[42]; // no owner/discriminator check
```

**Recommendation:** Replace `AccountInfo` with the strongly-typed `Account<'info, VaultState>`. Anchor will verify the owner program and discriminator automatically:
```rust
#[account(mut, has_one = admin, seeds = [b"vault"], bump = vault_state.vault_bump)]
pub vault_state: Account<'info, VaultState>,
```
Then read `vault_state.vault_bump` instead of indexing raw bytes.

**Reference:** [rules/002-missing-owner-check.md](rules/002-missing-owner-check.md)

### [CRITICAL] Rule 017: Unvalidated token_program AccountInfo in Deposit context allows arbitrary CPI

**File:** `src/lib.rs:183`

**Description:** In the `Deposit` accounts struct, `token_program` is typed as a raw `AccountInfo` with only a `/// CHECK:` comment and no actual program ID validation. An attacker can pass any program they control as `token_program`. The `deposit` instruction then calls `token::transfer` via a `CpiContext` built from this unvalidated account, meaning the CPI targets the attacker's program instead of `spl_token`. The fake program can return `Ok(())` without moving any tokens, but the program still credits the user's position with the deposited amount, allowing the attacker to gain protocol credit for free and later withdraw real tokens.

**Vulnerable code:**
```rust

```

**Recommendation:** Change `token_program` in the `Deposit` struct from `AccountInfo<'info>` to `Program<'info, Token>`, matching the `Withdraw` context. Anchor will then automatically verify the account key matches `spl_token::ID`. Remove the `/// CHECK:` comment.

### [HIGH] Rule 013: Non-canonical bump accepted in initialize_vault and stored without verification

**File:** `src/lib.rs:22`

**Description:** The `initialize_vault` instruction accepts `vault_bump: u8` as a caller-supplied argument and stores it in `vault_state.vault_bump`. Although the `InitializeVault` context uses Anchor's `bump` constraint (which derives the canonical bump), the caller-supplied `vault_bump` is stored and later used for CPI signer seeds in `withdraw` and `collect_fees`.     ...
}
```

**Recommendation:** Do not accept `vault_bump` as an instruction argument. Instead, retrieve the canonical bump from the Anchor context: `vault.vault_bump = ctx.bumps.vault_state;`. This guarantees only the canonical bump is stored and later used for CPI signing.

pub vault_authority: AccountInfo<'info>,
```

**Recommendation:** Use distinct seed prefixes for logically distinct PDAs. For example, use `[b"vault_state"]` for the state account and `[b"vault_authority"]` for the token authority PDA. This avoids conflation and potential confusion about account roles.

### [MEDIUM] Rule 025: Precision loss: division before multiplication in fee calculation

**File:** `src/lib.rs:96`

**Description:** The fee is computed as `amount / FEE_DENOMINATOR * vault_fee_bps as u64`. Because integer division is performed first, `amount / 10_000` truncates (rounds toward zero) before the result is multiplied by `fee_bps`. For any `amount < 10_000` the fee is always 0, and for larger amounts significant rounding error accumulates in every withdrawal, letting users consistently pay less than the intended fee.

**Vulnerable code:**
```rust
let fee = amount / FEE_DENOMINATOR * vault_fee_bps as u64;
let payout = amount - fee;
```

**Recommendation:** Multiply first, then divide: `let fee = (amount as u128).checked_mul(vault_fee_bps as u128).ok_or(VaultError::Overflow)?.checked_div(FEE_DENOMINATOR as u128).ok_or(VaultError::DivByZero)? as u64;` This preserves precision and avoids silent rounding to zero for small amounts.

**Reference:** [rules/025-precision-loss.md](rules/025-precision-loss.md)
